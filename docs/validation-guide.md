# 使い方と、これから行う実機検証

このガイドは、現在の実装を使って「取得できる」「目的の信号が通る」「必要な時間安定する」を順に確かめる手順です。往路・復路ともユーザーから動作確認の報告があり、復路はDiscrete4のMonitor mixを消音・復元した際にRME Software Playback 9/10のメーターが追従することも確認しました。名前を特定したFXの比較、最終物理出力の対応、実際の遅延、長時間運転は別途検証します。新しい設定では全ミュートの起動・停止から始め、確認できた経路を一つずつ増やします。

更新日: 2026-09-28。ビルド方法とCLIの詳細は [ビルドと使い方](getting-started.md)、済んだ試験は [実機試験記録](measurements/2026-09-28-initial-app/README.md) を参照してください。

## 画面の使い方

`dist/My Redirector.app` を開くと、メイン画面には **OFF / ON** のボタンだけが表示されます。**⌘,（Command + カンマ）**、またはアプリメニューの「設定…」で設定画面を開きます。設定は自動保存されますが、転送は毎回OFFから始まります。

初回の設定値は全入力Mute・復路Muteです。**2回目以降は保存したgain/muteも復元する**ため、起動時OFFであることと、全チャンネルがMuteであることは別です。試験を始めるたびに「ミックス」で確認してください。

| タブ | 主な操作 |
| --- | --- |
| 入出力 | RMEデバイス、Discrete4デバイス、PCの再生先と出力stream、復路の入出力L/Rを選ぶ |
| ミックス | RME INPUT・PC OUTPUTのgain/Mute/pan/LinkとGate、2MIXのMaster、RETURNのgain/Muteと左右Gateを調整する。下の項目はスクロールで表示する |
| 動作 | 要求 I/O、3経路のFIFO、SRC 品質、元のPC音声を抑えるかを選ぶ |
| 診断・取得テスト | 実際のI/O、callbacks/frames、FIFO不足・超過を見る。PC取得テストと診断の書き出しを行う |

gainの範囲は−90〜+12 dBです。**Muteにチェックがあると、そのチャンネルをミックスへ送りません。** `Link` は隣り合う奇数・偶数チャンネルのgain・Mute・Gate設定とGateの検出を連動させます。panは連動しません。初期panは奇数=L、偶数=Rです。1chずつ確認する際は、OFF中にそのペアのLinkを外します。

Panの表示はL=左、C=中央、R=右です。左右を初期配置へ戻したい場合は、OFF中に対象の取得元見出しの **「Panを奇数L・偶数Rに戻す」** を押します。その取得元の全chのPanだけを戻し、gain/Mute/Linkは変更しません。両chがRに寄っている状態は、LinkをONにするだけでは直りません。

**Spotify・ブラウザー・DAWなどの再生音はPC OUTPUT、RMEのMic/Line端子へ入る音はRME INPUTで調整します。** PCの再生先がRMEでも、PC OUTPUTとRME INPUTは別の取得元です。PC OUTPUTを全MuteにしたままMic入力のMuteを外しても、PC再生音を有効にしたことにはなりません。各見出しの取得元名と、操作する区画を照合してください。

今回のRME inventoryでは入力1/2は`Mic/Line 1`/`Mic/Line 2`、出力1/2は`Analog 1`/`Analog 2`で、Micの表示はデバイスが返す入力名です。

機器、チャンネル割当、I/O、FIFO、SRC品質、Linkの変更はOFF中に行います。転送中はgain/Mute/panとGateのON/OFF・各値を調整できます。PC取得テスト中はミックス操作も無効になります。

### Gateの使い方

ミックス画面の各RME INPUT・PC OUTPUT、およびRETURN左右にGateがあります。`Gate`のチェックで有効・無効を切り替え、`Threshold · dBFS`で開き始める入力レベルを調整します。各行の **「…」** からAttack・Hold・Release・Hysteresisを開きます。

Gateはチャンネルのgain・pan・Muteより前の入力を判定します。Thresholdを上げるほど小さい音を閉じやすくなります。必要な弱い音や残響まで切れる場合はThresholdを下げ、Releaseを長くするなど、同じ音源で調整してください。GateをOFFにすると、そのチャンネルはGateによる抑制を通さず、既存のgain・pan・Muteに従います。

| 項目 | 既定値 | 調整範囲・役割 |
| --- | --- | --- |
| Gate | ON | 旧保存データにGate設定がない場合もONで補完 |
| Threshold | −60 dBFS | −96〜0 dBFS。開くための入力レベル |
| Attack | 0.2 ms | 0.1〜50 ms。開く時の立ち上がり |
| Hold | 50 ms | 0〜1000 ms。閉じるレベルを下回ってから開いた状態を維持する時間 |
| Release | 30 ms | 1〜2000 ms。閉じる時の減衰時間 |
| Hysteresis | 6 dB | 0〜24 dB。開くレベルと閉じるレベルの差。既定では−60 dBFSで開き、−66 dBFSを下回るとHold・Releaseに従って閉じる |

Link中は左右の大きい方の入力で判定し、同じGate利得を左右へ掛けます。どちらの行から設定してもGate値は両方へ反映されます。OFF中にLinkを有効にすると奇数側のGate設定を偶数側へ合わせます。RETURNのLinkはGateだけを連動し、既定はONです。RETURNのgain/Muteは左右共通の復路操作です。

入力メーターはGate・Mute前なので、Gateが閉じていてもノイズのレベルは見えます。Gate表示の`OPEN`はほぼ全開、`抑制`は閉鎖または開閉の途中、`OFF`はGate無効です。`OPEN`でもMute中なら音声は送られません。実際の送出は2MIX/RETURNの送出メーターと送り先でも確認します。Gate利得の表示は直近callback末尾の値で、音声波形や区間全体の最大値ではありません。

Gate追加時も保存済みの経路・gain・Mute・panは維持され、アプリは起動時OFFです。新しいGate既定値が小さい信号へ作用するため、経路を切り分ける試験では対象のGateを一時的にOFFにして比較し、試験後に必要な値へ戻してください。

### Gate操作時に停止した場合

`fault 6` / `Audio timestamp discontinuity` は音声時刻の不連続を検出した停止です。Gateのしきい値エラーとは別で、新版は経路名と飛んだフレーム数も表示します。診断を書き出して、画面操作・音源・I/O値と一緒に記録します。再開前に原因を切り分け、異常判定を無効にして継続しません。

### PC FIFO不足からの自動復帰

PC側のFIFO不足ではONのまま続行します。不足したPC音声と蓄積済みの古いPC音声を破棄し、約1 msで無音へ移行、再びデータが揃うと約1 msで復帰します。RME入力のミックスとDiscrete4からの戻りは継続します。FIFO設定値は変更しません。

不足・復帰の回数と破棄/無音frame数は診断と `~/Library/Logs/My Redirector/events.jsonl` に残ります。音声処理とは別の処理で最大1秒ごとに集約して保存し、書込み失敗も診断の `eventLog` で確認できます。「動き続けた」と「音声欠落がなかった」は別に評価し、不足回数が増える設定を無欠落の安定動作とは扱わないでください。機器切断・時刻不連続・PC以外の不足等は引き続き停止対象です。

Gateを全42chで毎秒約42回更新する実機比較では、有効・無効の両方で60秒成功しました。一方、GUI試用中の同時callback遅着は原因の切り分けを継続中です。[GUI/Gateの実装](gui-and-gate.md)と[試験条件・結果](measurements/2026-09-28-gui-gate/README.md)を参照してください。

## 0. 機器とチャンネル対応を確認する

Macと各機器のUSB接続を使います。機器間のS/PDIF・ADATケーブルは撤去済みです。この手順で再接続したり、RMEとDiscrete4を結合したAggregate Deviceを作ったりする必要はありません。

先に現在のTotalMixとDiscrete4の画面を確認し、使っている経路を控えてください。アプリは機器のclock source、sample rate、macOSの既定出力、TotalMixやDiscrete4内部のroutingを自動変更しません。48 kHzで動作していることを確認します。Discrete4のUSB動作中にClock Source表示がUSBになることだけを、直ちに異常とは判定しません。

「入出力」で「デバイス一覧を更新」を押し、次を照合します。数値は今回の観測であり、接続・ドライバー・機器モードが変われば再確認が必要です。

| 項目 | 今回の観測と選び方 |
| --- | --- |
| RMEデバイス | Fireface UCX II。20入力・20出力を観測。RME INPUTの表示はCore Audioの入力順で、各物理端子との対応を後で1chずつ確認する |
| PCの再生先 | 初期試験は既存の「5.1ch」、追加確認では物理RMEも対象にした。実際に試験音を再生するアプリ/DAWの出力先と照合する。システム既定出力とDAW個別の出力設定を混同しない |
| 出力 stream | 今回は **stream 0、20ch**。device名が5.1chでも、取得formatが6chとは限らない。stream番号は0始まり、画面のch番号は1始まり |
| Discrete4デバイス | 16入力・16出力を観測。アプリからの送信先は **Computer Play 1/2固定** |
| Discrete4の「処理後入力 L/R」 | 今回は **USB 7/8**。DAW Record 7/8に`LOOPBACK HP1/MON 1/2`の実表示を確認した。以前選んでいたUSB 1/2はPREAMP 1/2だった |
| RMEの「復路 L/R」 | RMEの **Software Playback（host playback）** の送り先。現在は **9/10（SPDIF表示）**。TotalMixのHardware Outへの割当と実音到着は別に確認する |

今回の初代Discrete4では、SAVE ASで保存したプリセットを基準にLoopback経路を設定し、通常のLOAD後にDAW Record 7/8の割当を実表示で確認しました。その後、Monitor Mixer#0だけを一時的に全入力消音すると、元PC音声のメーターが続く一方でRME復路9/10がUFLになり、設定復元後に信号が戻ることを確認しました。**mix後のUSB復路は実信号で確認済みですが、名前を特定したFXの比較と最終物理出力は未検証です。** ソース選択のGUIが開かなかったことだけで非対応と判断せず、世代・現在の設定・実表示を分けて確認します。変更範囲・結果・バックアップは [復路設定記録](measurements/2026-09-28-return-fix/README.md) にあります。別の機器へ今回のプリセット値をそのまま適用する手順ではありません。

今回使ったslot7/8は元が未使用のS/PDIF入力で、4つのMixerすべてでそのLoopbackスロットをMuteにしました。Loopbackを元のMixerへ混ぜ戻す循環を作らないよう、録音先の番号だけでなく共有ソース枠と各Mixerの状態も照合します。検証を始める際は、現保存設定がRETURN Mute解除であることに注意し、まずOFF中にRETURNをMuteしてください。全ミュートのI/O試験は、復路の信号内容を検証したことにはなりません。

「表示中の対応を確認」は、確認したチャンネル名・stream対応をアプリに保存する操作です。音声を通したり、機器側の経路を変更・検証したりするボタンではありません。表示と接続先が一致した後に押してください。

## 1. 全ミュートで起動・停止する

1. 他の試験音を止め、「ミックス」でRME INPUTとPC OUTPUTの全Mute、RETURNのMuteを確認します。初回比較は「動作」で **要求 I/O=32、3つのFIFO=32、SRC 品質=Fastest** に揃えます。この組合せは全ミュート60秒の成功実績がある試験用の出発点です。
2. 「取得中は元の process 出力を抑える」はOFFにしておきます。この状態での全ミュートは **My Redirectorの出力だけ** に効き、他アプリの元の再生音は消しません。
3. メイン画面のOFFを押して開始します。必要なmacOSの音声入力/システム音声取得許可が表示されたら内容を確認して許可します。準備中は連打せず、「診断・取得テスト」が **ON · 転送中** になることを確認します。
4. 60秒程度、RME・PC・Returnのcallbacks/framesが増えること、「実際の I/O」が要求した値であること、「不足 / 超過」と「Clip / 非有限値」が0であることを確認します。入力はMute中も取得するため、入力メーターの動き自体は出力漏れを意味しません。
5. 「診断を書き出す…」で運転中の記録を保存し、メイン画面のONを押して停止します。診断のOFF表示を確認し、停止後の記録も別名で保存します。

同じ条件で起動・停止を数回繰り返し、毎回準備が完了し、停止後に再び設定を変更できることを確認します。全ミュートの成功は、USB入力に目的の信号が入っていることや、最終物理出力から音が出ることを保証しません。

## 2. PC音声を1音源・1chずつ確認する

最初は取得だけを調べ、その後Discrete4までの往路を調べます。モニターは小さい音量から確認し、RME INPUTとRETURNは引き続き全Muteにします。

物理RME対象のTapで非ゼロ信号を取得した追加記録がありますが、別時点の5.1ch対象試験との比較だけでは音源や適切な取得先を確定できません。[PC OUTPUT確認記録](measurements/2026-09-28-pc-output-fix/README.md)。同じ音源・出力先・再生状態で以下を確認します。

1. 転送をOFFにし、試験するアプリ/DAWを一つに絞ります。その出力先が「入出力」のPC再生先と一致することを確認し、低レベルの短い音を1chへ送ります。再生アプリが出力chを指定できない場合は、対応を確認できる範囲だけ記録します。
2. 「診断・取得テスト」の **PC取得テスト** を押します。formatが48 kHz・意図したch数で、callbacksが増え、意図したchのメーターが動くかを確認します。左のみ、右のみ、その後使用する残りのchを順番に確認し、「再生アプリのch → Tapのch」の表を残します。
3. **取得テストを停止** を押します。このテストはMy RedirectorからRME/Discrete4へ音声を出しませんが、元の再生音は通常どおり残ります。
4. OFF中に試験ペアのLinkを外し、PC OUTPUTの試験対象だけgainを例えば−30 dBに下げます。2MIXのMasterを0 dBに揃え、対象1chだけMuteを外して転送をONにします。ほかのPCチャンネルはMuteのままにします。
5. Discrete4の **Computer Play 1/2** のメーターで到着を確認します。試験対象のMuteで消え、gainでレベルが変わり、panのL/Rと到着先が対応することを確認します。元音声が別経路でも聞こえる場合は、この段階では聴感だけで到着を判定しません。
6. 1chずつ確認して転送をOFFにしてから、必要なstereoペアをLinkします。再度ONにして、左右のgain/Muteが連動しつつpanが保たれることを確認します。終了時は対象をMuteに戻し、転送をOFFにします。

## 3. RME入力を1chずつ確認する

TotalMixで、取得する入力ペアに対応するHardware OutのLoopbackが既に有効になっていないか確認します。有効なペアではCore Audioの録音入力が出力サブミックスに置き換わるため、物理入力を読んだ確認にはなりません。既存設定を控え、物理入力を取得するペアはLoopbackを使わない状態で検証します。

PC OUTPUTとRETURNを全Muteにし、PCの試験音を止めます。既存のRME入力へ低レベルの信号を一つだけ入れ、RME INPUTも全MuteのままONにして、どのchの入力メーターが動くかを確認します。端子名とアプリのch名を記録し、転送をOFFに戻します。

OFF中に試験ペアのLinkを外し、対象gainを低くして、そのchだけMuteを外します。ONにしてDiscrete4 Computer Play 1/2への到着、Mute、gain、panを確認します。入力を替えて必要なchを順に試し、最後にPC入力と一つずつ組み合わせて2mixを確認します。ここでもRETURNはMuteのままです。RME Loopbackを有効にする必要はありません。

## 4. Discrete4のFX後音声をRMEへ返す

先に手順0の対応を確認します。今回の割当は **Monitor/HP1 Loopback L/R → DAW Record 7/8 → アプリUSB入力7/8 → RME Playback 9/10** で、mix全入力の消音・復元が復路へ反映することを実信号で確認済みです。Master Out 1/2が、そのままUSB Record1/2へ複製されるとは仮定しません。以下ではまだ残る左右・FX・物理出力・gain/Muteを確認します。他の設定では現在のroutingを控え、処理後ミックスの送り先を確認できなければ実音試験を保留します。

1. 転送OFF・RETURN Muteの状態で、確定したUSB番号をDiscrete4の「処理後入力 L/R」に選びます。
2. RMEの「復路 L/R」を選び、そのSoftware PlaybackペアがTotalMixでどのHardware Outへ流れるかを確認します。番号選択だけでTotalMixのroutingが変わることはありません。既存のモニター経路を変更する必要があれば、現在の割当を記録してから必要な箇所だけを検討します。
3. 往路で確認できたPCまたはRMEの1音源だけを低レベルで有効にし、RETURN gainも例えば−30 dBに下げます。ONにしてからRETURNのMuteを外し、選んだRME Software Playbackと、その先の意図した物理出力で確認します。
4. 左のみ/右のみの短い音で対応を確認します。既に使っているFXのbypass切替など、処理前後の違いを識別できる条件で、返ってくるのがFX後の音か確認します。単に音が戻っただけではPREAMPやComputer Playの直接コピーと区別できません。
5. RETURNのMuteで復路だけが止まり、gainで復路レベルが変わることを確認します。別のRME出力ペアを使う場合も、OFFで選び直し、同じ確認を繰り返します。

Discrete4のMonitor mixに入れるComputer Playのフェーダーが最小・Mute有効なら、Computer PlayのPlayメーターが動いていてもmixには入りません。今回この状態だったslot5/6は0 dB・Mute解除へ変更済みで、消音反応試験後も同じ状態へ復元し、Soloは全解除を確認しました。確認時は左右のpanと他の音源も照合し、Loopback自身のslot7/8は全MixerでMuteを維持します。今回GUIのSolo/Mute単独操作はDSP追従が曖昧だったため、表示変化だけを音声への反映成功と扱いません。物理Monitor主音量、DIM、Mute、AuraVerbが復路へ作用する位置は別の確認項目で、通常の入力フェーダーやAFXと混同しません。

## 5. 循環と二重再生がないか確認する

アプリは自分がRMEへ返した音をPC Tapから除外する設計ですが、実信号での確認は別に必要です。TotalMix、Discrete4内部mix、他の録音/モニターアプリを含めて経路を確認します。

1. 確認済みの1音源で短い音を送り、音源を停止します。FXの意図した残響・ディレイが終わった後もPC入力や往路へ戻り続けたり、レベルが増え続けたりしないことを確認します。異常時はメイン画面でOFFにし、同じ設定で繰り返しONにしません。
2. RETURNをMuteした時に止まる音と、元のPC再生経路で残る音を区別します。両方が同じスピーカーへ届く場合は、二重再生による音量変化や時間差がないか確認します。
3. 元音声の抑制が必要な場合だけ、OFF中に「動作」の **取得中は元の process 出力を抑える** をONにして比較します。対象アプリの別用途の出力、取得開始時、転送停止時、PC取得テスト時にも影響を確認します。期待と違えばOFFへ戻します。
4. RME復路の送り先を変更して使う場合、その送り先でも自己音声除外と二重再生を確認します。自己除外はAESの特定番号だけに依存する設計ではありません。

## 6. I/OとFIFOを別々に比較する

信号経路が確認できてから、小さい設定を比較します。以下は **全ミュート・短時間・今回の環境** の実績です。成功行も常用の安定性を保証するものではありません。

| 要求 I/O | FIFO RME → D4 / PC → D4 / D4 → RME | 実測結果 |
| --- | --- | --- |
| 16 | 16 / 16 / 16 | 約28秒でRME側不足、停止 |
| 16 | 32 / 32 / 32 | 60秒成功 |
| 32 | 32 / 32 / 32 | 60秒成功 |
| 64 | 64 / 64 / 64 | 10秒成功、追加60秒試験では約37秒でPC側不足 |
| 64 | 64 / 128 / 64 | 60秒成功 |

初めはSRC品質と音源を固定し、FIFOを32/32/32のままI/O32と16を比較します。その後、I/Oを固定し、**一経路のFIFOだけ** を変更します。全ミュートで起動・停止を確認してから、同じ実音・同じ時間で比較してください。不足が出た経路、発生時刻、CPU、使用アプリ、操作内容を記録します。単にI/Oが小さい設定ほど安定すると考えないでください。

初期実装では、各FIFO目標がその経路のsource/destinationの最大実I/O block以上でなければ開始できません。RME往路と復路はRME/Discrete4、PC往路はTap/Discrete4を比較します。I/O64でFIFO32にはできず、要求I/Oと実際の読み戻しが異なる場合も拒否します。勝手に大きな値へ置き換えて開始することはありません。

| 数値 | 意味と見方 |
| --- | --- |
| I/O frames | デバイスcallbackのブロック長。48 kHzでは16=約0.333 ms、32=約0.667 ms、64=約1.333 ms。経路全体の遅延ではない |
| FIFO目標 | ソフト内で待つsource framesの目標。render後の平均占有を制御するための値で、常にその数だけ溜まっているという意味ではない |
| ASRC / ppm | 独立したクロックのずれを継続補正する処理と補正量。ppmが0でないことだけで異常とは判定しない。SRC内部の先読み・処理時間はFIFOと別 |
| 実遅延 | 取得・I/O位相・FIFO・ASRC・Discrete4内処理・出力等を含む実際の経路の時間。**現在は未測定**で、上の設定値を足しただけでは確定しない |

実遅延は、入力の短いパルスと目的の最終出力を同じ時間基準で記録し、差を測る別試験が必要です。測定経路が循環しないこと、比較する録音経路の遅延をどう扱うかを先に決め、LadioCastとも同じ経路・同じ音源・同じ測定条件で比較します。ASRCのFastest/Medium比較も、I/O/FIFO等を固定して別に行います。

## 7. 長時間運転を確認する

実音経路を確認した設定を一つ選び、GUIから手動でONにして、まず30分、次に2時間、8時間、必要なら24時間と延ばします。通常使うアプリを動かした状態、設定画面を閉じた状態/開いた状態、タブ切替や通常スクロールを行う状態も記録します。短時間の成功結果だけで先の段階を省略しません。

開始直後・中間・終了直前に「診断を書き出す…」で別ファイルへ保存し、音切れ、音量変化、エラー、FIFO不足・超過、Clip/非有限値、機器rate変更を確認します。診断の書き出しはその時点のスナップショットであり、連続イベントログや音声録音ではありません。異常の時刻・直前の操作は別にメモしてください。

終了時はメイン画面からOFFにし、停止後の診断も保存します。長時間の合格には、転送中の安定だけでなく正常停止と再開を含めます。**既存の `--probe-config` と `--check-muted-route` は最長60秒です。** このCLIを8時間指定したり、繰り返し起動した結果を1回の連続長時間運転と扱ったりせず、長時間はGUIで手動確認します。

## エラーや待ちが出た時に残すもの

「OFF · エラー」や赤いエラー表示が出たら、再起動前に「診断を書き出す…」を保存します。不足なら発生した経路、rate/formatなら実際の値、mapping不一致なら現在のチャンネル名を確認します。「表示中の対応を確認」で無条件にエラーを消さず、物理・論理の対応を照合してから再設定してください。再試験は全Muteから始めます。

| 記録項目 | 例 |
| --- | --- |
| 開始/終了時刻と試験時間 | 18:00〜18:01、60秒 |
| 音源と確認範囲 | PCの1ch、D4 Computer Play到着まで。復路は未検証 |
| 設定 | 48 kHz / I/O32 / FIFO32,32,32 / Fastest / 元音声抑制OFF |
| 経路 | PC device/stream/ch、D4 USB復路L/R、RME Playback L/R、TotalMixの物理出力 |
| 結果 | callbacks進行、不足/超過、fault、聞こえた音、終了後OFF |
| GUIの待ち | タブ名、押した操作、待った秒数、通常のマウス操作か自動操作か |

ミックスタブのレイアウトを軽くする修正は済み、タブ切替と表示を再確認しました。一方、自動操作の最下部スクロールで失敗が残っています。通常スクロールも含めた全GUIの安定確認が済んだとはしていません。画面の待ち時間と音声FIFOの不足は別に記録します。[GUI調査記録](measurements/2026-09-28-initial-app/gui-investigation.md)
